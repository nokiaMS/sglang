- 模型格式差异：deepseek-ai/DeepSeek-V4-Pro vs sgl-project/DeepSeek-V4-Pro-FP8
  - MoE专家权重精度
    - 原始版（deepseek-ai/DeepSeek-V4-Pro）：FP4（mxfp4-packed，存储为U8/I8/F4）
    - FP8版（sgl-project/DeepSeek-V4-Pro-FP8）：FP8（F8_E4M3）
  - 非专家权重精度
    - 两版均为FP8，无差异
  - 转换方式
    - FP8版为纯格式转换（FP4→FP8反量化），无微调/重训练，架构/Tokenizer/Chat模板完全不变
  - 支持的并行模式
    - 原始FP4版：仅支持张量并行（TP），MoE内核使用 `--moe-runner-backend marlin` 或 `flashinfer_mxfp4`，单节点8卡（TP=8）即可运行完整Pro模型
    - FP8版：支持 TP + DP + EP + DeepEP + DP-Attention + Context Parallel + PD-Disagg 全部并行模式，可多节点部署
  - 环境变量
    - 原始FP4版：`SGLANG_DSV4_FP4_EXPERTS` 默认为 True（自动检测）
    - FP8版：必须设 `SGLANG_DSV4_FP4_EXPERTS=0`
  - 磁盘占用
    - FP8版更大（FP4→FP8，专家权重体积约翻倍）
  - 精度差异
    - 极小，sglang官方benchmark中两种格式使用相同的准确率基线
  - 为什么多节点部署必须用FP8版
    - DeepEP的跨节点all-to-all通信机制需要FP8格式的专家权重；原始FP4格式通过Marlin内核执行，该内核仅支持TP模式，不支持跨节点EP
- 注意事项
  - 模型格式：使用DeepEP多节点部署需FP8格式的模型权重。如果`/userdata/dsv4/DeepSeek-V4-Pro`为原始FP4权重，需替换为FP8重打包版本（HuggingFace: `sgl-project/DeepSeek-V4-Pro-FP8`）。原始FP4格式仅支持单节点TP模式，不支持DeepEP和EP。
  - 启动顺序：先启动节点0（--node-rank 0），再启动其他节点。所有节点需在dist_timeout内完成连接。
  - 上下文长度：--context-length 1048576为模型官方最大值。如遇OOM，可降低该值（如524288或262144）。
  - 网络要求：多节点间需RDMA/InfiniBand网络互通，确保端口20000未被占用。
  - watchdog超时：DeepSeek-V4-Pro首次加载+DeepGEMM预热可能需要10+分钟，建议设置`--watchdog-timeout 3600`。
- 显存分析（基于sglang源码DSV4PoolConfigurator）
  - 模型参数（来自config.json）
    - head_dim=512, qk_rope_head_dim=64, qk_nope_head_dim=448
    - num_hidden_layers=61, n_routed_experts=384
    - compress_ratios: 31层c128 + 30层c4 + 1层full
    - swa_page_size=128, index_head_dim=128
  - 每GPU显存预算（H100 80GB）
    - 总显存：80 GB
    - 静态分配（mem-fraction-static=0.88）：70.4 GB
    - 模型权重（FP8, TP=32分片）：~48 GB/GPU
    - 剩余KV cache空间：~22.4 GB/GPU
  - KV cache每token成本（DSV4PoolConfigurator._get_bytes_per_full_token）
    - kv_bytes = 448 + 64*2 + 8 = 584 bytes（qk_nope FP8 + qk_rope BF16 + scale）
    - indexer_bytes = 128 + 4 = 132 bytes
    - c4_state_bytes = 8192, c128_state_bytes = 4096, c4_indexer_state_bytes = 2048
    - **bytes_per_full_token ≈ 183,211 bytes（约179 KB/token）**
  - 容量计算
    - 每GPU最大token数：22.4 GB / 183,211 ≈ 131,000 tokens
    - 32个GPU总KV cache容量：~4.2M tokens
    - 256并发 × 1M上下文 = 268M tokens → **远超容量，无法同时承载**
  - 实际可行配置
    - --context-length 1048576 可以设置，它仅限制单请求最大长度，不会预分配满额KV cache
    - sglang会根据实际KV cache容量自动限制max_running_requests
    - 最大吞吐模式下，实际并发约 131,000 / 平均请求长度 个请求
    - 典型场景（平均输入1K + 输出1K ≈ 2K tokens/请求）：~65并发/GPU，32 GPU总计约可达256+并发
    - 长上下文场景（50K输入 + 200输出 ≈ 50K tokens/请求）：~2.6并发/GPU，32 GPU总计约83并发
    - 1M上下文请求：同时只能运行约1-2个（受KV cache总容量限制）
  - 结论
    - 当前配置可正常启动运行，sglang不会因显存不足报错
    - --context-length 1048576 和 --max-running-requests 256 是上限约束，实际并发由sglang根据KV cache容量自动调整
