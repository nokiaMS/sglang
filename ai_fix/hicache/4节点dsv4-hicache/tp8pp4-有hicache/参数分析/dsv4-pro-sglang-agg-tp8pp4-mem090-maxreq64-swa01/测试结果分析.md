# DeepSeek-V4-Pro TP8PP4 HiCache 性能测试分析（swa_full_tokens_ratio=0.1）

## 测试配置

- 模型: DeepSeek-V4-Pro
- 硬件: 4节点 × 8×H800 80GB (32 GPU)
- 框架: sglang v0.5.12.post1
- 并行: TP=8, PP=4
- HiCache: enabled (ratio=2.0, write_through, direct IO)
- mem-fraction-static: 0.90
- max-running-requests: 64
- swa-full-tokens-ratio: 0.1（默认值，未显式传参）
- 代码修复: hybrid_pool_assembler.py start_layer 偏移修复

## 关键发现

### 1. HiCache 预热效应极其显著

这是本次测试最突出的特征：**三轮测试间性能逐轮大幅提升**，远超正常波动范围：

**C10:**
- R1→R3: Input throughput 5904→7658 (+30%), TTFT 2194→1137 (-48%)

**C30:**
- R1→R3: Input throughput 11699→21991 (+88%), TTFT 7133→3284 (-54%), TPOT 961→424 (-56%)

这表明 HiCache 在前两轮压测中逐步将 KV cache 从 GPU 迁移到 Host，R3 时 host cache 已大量命中，prefill 阶段跳过了大量重复 token 的计算。

### 2. C60 OOM 崩溃

C60 并发下服务在第一个请求批次就触发 `Prefill out of memory`，所有 8 个 TP scheduler 均崩溃。原因分析：
- swa_full_tokens_ratio=0.1 意味着仅 10% 的 full KV 在 GPU 上保留（SWA 窗口很小）
- C60 并发下 60 个请求同时 prefill，每个请求 50K input tokens，需要大量临时显存
- 小 SWA 窗口虽然节省了 KV cache 常驻内存，但 prefill 时的临时内存需求并未减少
- mem-fraction-static=0.90 已将 90% 显存分配给 KV cache，留给 prefill 中间激活的空间不足

### 3. 与 swa_full_tokens_ratio=0.2 的对比

| 指标 | swa=0.2 C10 均值 | swa=0.1 C10 均值 | swa=0.2 C30 均值 | swa=0.1 C30 均值 |
|------|-----------------|-----------------|-----------------|-----------------|
| Input throughput (tok/s) | 5974 | 6642 | 11653 | 16093 |
| Output throughput (tok/s) | 29.5 | 32.8 | 46.2 | 63.7 |
| Mean TTFT (ms) | 2020 | 1732 | 7021 | 5633 |
| Mean TPOT (ms) | 303 | 272 | 958 | 738 |

swa=0.1 在低并发下（C10/C30）吞吐量更高、延迟更低，因为更多 KV cache 被卸载到 Host，GPU 常驻内存占用更少。但代价是 C60 直接 OOM，而 swa=0.2 可以成功运行 C60。

### 4. 性能稳定性差

三轮测试结果方差极大，特别是 C30：
- Input throughput: 11699→14588→21991 (几乎翻倍)
- Mean TTFT: 7133→6482→3284 (减半)

这种逐轮递增的模式说明系统尚未达到稳态，HiCache 的填充和命中需要时间。实际生产环境中，随着 cache 逐步填满，性能会从 R1 水平逐步提升至 R3 水平。

### 5. 延迟分布

- **TTFT 长尾严重**: C30 R1 的 P99 TTFT 达 34.7s（中位 2.6s），部分请求在队列中等待极久
- **TPOT 双峰分布**: C30 R1 中位 TPOT 547ms vs 均值 961ms，高并发下调度抖动显著
- **ITL 尾延迟**: C30 R1 Max ITL 32s，C10 R1 Max ITL 10s

## 建议

1. **swa_full_tokens_ratio 取值**: 0.1 虽然在低并发下性能更优，但无法承载 C60 并发。建议使用 0.2 或更高值以获得更好的高并发稳定性
2. **HiCache 预热**: 生产环境部署后应有预热阶段，逐步填充 host cache 至稳态后再承接流量
3. **降低 C60 OOM 风险**: 可考虑增大 swa_full_tokens_ratio、降低 max-running-requests、或优化 prefill 分块策略
4. **结果取值**: 由于 HiCache 预热效应，R1 最接近冷启动性能，R3 接近稳态性能。报告中应同时呈现冷启动和稳态数据
