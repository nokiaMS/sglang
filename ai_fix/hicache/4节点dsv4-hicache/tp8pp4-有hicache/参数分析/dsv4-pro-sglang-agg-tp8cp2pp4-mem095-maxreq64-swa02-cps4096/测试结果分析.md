# 测试结果分析

## 测试结论

- `TP=8, CP=2, PP=4, DP=1` 可以在当前 4 节点 H800 环境中启动，并完成 C10、C30、C60 三组压测。
- 服务端日志中出现 `ATTN_CP0` 和 `ATTN_CP1`，说明 `--attention-context-parallel-size 2` 已生效。
- 9 轮压测全部成功，每轮 `Successful requests` 均为 100，测试过程中未观察到服务崩溃。
- 与原基线 `TP=8, PP=4, DP=1` 相比，加入 `CP=2` 后吞吐没有提升，整体略有下降；当前不建议把 CP=2 作为默认性能配置。

## 参数

```text
TP=8
attention-context-parallel-size=2
PP=4
DP=1
HiCache=enabled
mem-fraction-static=0.95
max-running-requests=64
swa-full-tokens-ratio=0.2
chunked-prefill-size=4096
disable-cuda-graph=true
disable-overlap-schedule=true
```

## 分析

- CP=2 后，attention 被拆成两个 context parallel 组，日志中的 rank 前缀从 `PPx TPx` 变为 `PPx ATTN_CPx TPx`，说明调度路径和通信拓扑发生变化。
- 当前测试输入长度为 50000，确实属于较长上下文场景，但在该负载下 CP=2 带来的 attention 计算切分收益没有覆盖额外通信和调度开销。
- C60 场景下降幅度最大，说明高并发下 CP 额外通信对端到端吞吐和 TTFT 的影响更明显。
- 源码约束层面，当前参数满足 `tp_size % attn_cp_size == 0` 和 `tp_size % (dp_size * attn_cp_size) == 0`，并且 `DP=1` 避开了此前 `PP + multi-node DP attention` 的 `_dp_max_padding` 问题。

## 建议

- 当前最佳默认配置仍建议使用 `TP=8, PP=4, DP=1`，不加 CP。
- `TP=8, CP=2, PP=4` 可以作为可启动、可完成压测的对照组保留，但不建议用于追求最高吞吐的主配置。
- 如果继续验证 CP，建议只在更长输入、更高 context-length 压力或显存压力场景下测试；当前 50000 输入长度和 C10/C30/C60 压测没有体现收益。
