# dsv4-pro-sglang-agg-tp4dp2pp4-mem095-maxreq64-swa02-cps4096 测试结果分析

## 结论

本次失败的直接根因是 SGLang 在 `TP=4 DP=2 PP=4 + --enable-dp-attention` 路径下，PP 阶段接收 proxy tensor 时触发 DP attention 的 buffer 对称性判断，但 `_DpGatheredBufferWrapper._dp_max_padding` 尚未初始化，导致 scheduler 子进程抛出 `AttributeError` 并退出。

随后其他 PP stage 在等待上游/下游通信时看到 `gloo Connection closed by peer`，HTTP 服务进程也因 scheduler 初始化失败而退出，bench 侧最终表现为 `ConnectionRefusedError`。因此 `ConnectionRefusedError` 和 gloo 断连都是级联现象，不是最初根因。

## 实际执行配置

| 参数 | 值 |
| --- | --- |
| tp-size | 4 |
| dp-size | 2 |
| pp-size | 4 |
| enable-dp-attention | true |
| nnodes | 4 |
| mem-fraction-static | 0.95 |
| max-running-requests | 64 |
| swa-full-tokens-ratio | 0.2 |
| 启动参数 chunked-prefill-size | 4096 |
| 实际 chunked-prefill-size | 2048 |

首次只添加 `--dp-size 2` 时，服务在参数检查阶段失败：

```text
AssertionError: multi-node data parallel is not supported unless dp attention!
```

源码位置：`sglang/srt/server_args.py` 的 `check_server_args()` 明确限制 `dp_size > 1 && nnodes != 1` 时必须开启 `enable_dp_attention`。因此补充 `--enable-dp-attention` 后重新测试。

补充 DP attention 后，`server_args._handle_data_parallelism()` 会执行：

```text
chunked_prefill_size = chunked_prefill_size // dp_size
```

所以本次虽然启动命令传入 `--chunked-prefill-size 4096`，实际日志中变为 `chunked_prefill_size=2048`。

## 失败链路

1. 服务启动后，pod0 一度进入 HTTP ready：

```text
Uvicorn running on http://0.0.0.0:8080
```

2. C10 R1 warmup 开始后，node1 的 scheduler 首先出现源码级异常：

```text
AttributeError: type object '_DpGatheredBufferWrapper' has no attribute '_dp_max_padding'
```

3. 对应调用栈：

```text
scheduler_pp_mixin.py:event_loop_pp()
  -> _pp_recv_proxy_tensors()
  -> _pp_recv_typed_dict()
  -> pp_group.recv_tensor_dict(...)
  -> all_gather_group.all_gather(...)
  -> is_allocation_symmetric()
  -> is_dp_max_padding()
  -> _DpGatheredBufferWrapper.is_dp_max_padding()
```

4. 源码中 `_DpGatheredBufferWrapper` 只声明了 `_dp_max_padding: bool`，没有默认赋值；它只会在 `set_dp_buffer_len(...)` 中赋值：

```python
class _DpGatheredBufferWrapper:
    _dp_max_padding: bool

    @classmethod
    def set_dp_buffer_len(..., dp_max_padding: bool, ...):
        cls._dp_max_padding = dp_max_padding
```

5. 本次异常说明在 PP 接收 proxy tensor 的 all-gather 路径里，代码先调用了 `is_allocation_symmetric()`，但当前 scheduler 进程尚未执行过 `set_dp_buffer_len(...)` 初始化 `_dp_max_padding`。

6. `run_scheduler_process()` 捕获异常后会向父进程发送 `SIGQUIT`。这解释了后续日志：

```text
Scheduler or DataParallelController terminated with -3
Application startup failed. Exiting.
```

7. 其他节点的 `gloo Connection closed by peer` 是因为某个 scheduler 已退出，PP 通信对端关闭：

```text
RuntimeError: ... gloo/transport/tcp/pair.cc:547 Connection closed by peer
```

8. bench 侧 warmup 请求再次访问 `127.0.0.1:8080` 时，HTTP 服务已退出，因此报：

```text
ConnectionRefusedError: [Errno 111] Connect call failed ('127.0.0.1', 8080)
```

## 为什么这个配置会触发

本配置同时满足：

| 条件 | 影响 |
| --- | --- |
| `dp_size=2` 且 `nnodes=4` | 必须启用 DP attention |
| `pp_size=4` | 请求需要通过 PP stage 间传递 proxy tensor |
| `enable_dp_attention=True` | PP 接收 tensor 时会走 DP attention 相关 all-gather/symmetric allocation 判断 |
| `disable_cuda_graph=True` | 没有走某些 cuda graph runner 中预先设置 DP buffer 长度的路径 |
| C10 warmup 使用 50k 输入 | warmup 首个真实请求触发 PP/DP 调度链路 |

因此失败点不是显存不足。日志中可见各节点仍有可用 GPU 显存，例如 node0 约 10.88GB、node1 约 12.86GB、node2 约 13.01GB、node3 约 8.17GB；崩溃栈也没有 OOM，而是 Python 属性未初始化。

## 判断

当前 SGLang 版本在 `PP + multi-node DP attention` 组合下存在初始化顺序问题：`_DpGatheredBufferWrapper._dp_max_padding` 在某些 PP 接收路径被读取前没有保证初始化。该问题与本次添加 DP 的配置强相关，不是压测脚本、端口、dist-init-addr 或 HiCache start_layer 修复导致的直接问题。

## 建议

1. 在 SGLang 源码中给 `_DpGatheredBufferWrapper._dp_max_padding` 设置默认值，或在 `is_dp_max_padding()` 中处理未初始化状态。
2. 更稳妥的修复是确保所有 DP attention + PP scheduler 进入 `_pp_recv_proxy_tensors()` 前已调用 `set_dp_buffer_len(...)`。
3. 修复后先用低压请求验证链路，例如 `random-input-len=1000`、`num-prompts=1`、`max-concurrency=1`。
4. 若只验证 DP 本身，可先去掉 HiCache 或降低到更简单并行组合，隔离 `PP + DP attention` 的初始化问题。
