# 测试结果分析

## 测试配置

- 模型：DeepSeek-V4-Pro
- 硬件：4 节点，每节点 8 张 NVIDIA H800 80GB，总计 32 张 GPU
- 并行参数：TP=8, CP=2, PP=4, DP=1
- 关键参数：`--chunked-prefill-size 8192`，`--attention-context-parallel-size 2`
- HiCache：开启
- 其他参数：`--mem-fraction-static 0.95`，`--max-running-requests 64`，`--swa-full-tokens-ratio 0.2`，`--disable-cuda-graph`，`--disable-overlap-schedule`

## 启动结论

本配置可以在当前 4 节点 H800 环境中正常启动服务，并完成 C10、C30、C60 三组压测。node0 日志出现 `The server is fired up and ready to roll!`，压测过程中未在服务日志中发现 `Traceback`、`ERROR`、`RuntimeError`、`OutOfMemory`、`CUDA error` 或 `Exception`。

## 压测结果

| 并发 | Total token throughput R1 | R2 | R3 | 平均值 | Mean TTFT 平均值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| C10 | 6048.89 | 6053.20 | 6002.56 | 6034.88 tok/s | 2063.27 ms |
| C30 | 10380.40 | 10524.99 | 10663.13 | 10522.84 tok/s | 5539.83 ms |
| C60 | 11669.79 | 12599.70 | 12808.17 | 12359.22 tok/s | 25159.77 ms |

三组压测每次均为 100 个请求，全部成功。

## 对比结论

与 `tp8cp2pp4 + chunked-prefill-size 4096` 相比，本次 `chunked-prefill-size 8192` 性能更低：

| 并发 | CP2 + cps4096 平均 | CP2 + cps8192 平均 | 变化 |
| --- | ---: | ---: | ---: |
| C10 | 6130.36 | 6034.88 | -1.56% |
| C30 | 10938.85 | 10522.84 | -3.80% |
| C60 | 12985.71 | 12359.22 | -4.82% |

与当前已知最佳基线 `tp8pp4 + chunked-prefill-size 4096` 相比，本配置也更低：

| 并发 | TP8PP4 cps4096 平均 | CP2 + cps8192 平均 | 变化 |
| --- | ---: | ---: | ---: |
| C10 | 6387.43 | 6034.88 | -5.52% |
| C30 | 11341.47 | 10522.84 | -7.22% |
| C60 | 13842.46 | 12359.22 | -10.71% |

## 分析

`--attention-context-parallel-size 2` 可以把 attention context 在 CP 维度拆分，但在当前测试负载下没有转化为吞吐收益。此前 CP=2 + cps4096 已低于 TP8PP4 基线，本次把 `--chunked-prefill-size` 从 4096 提升到 8192 后，C10/C30/C60 均继续下降，且并发越高下降越明显。

主要原因判断是：8192 的 chunk 会增大单次 prefill 调度粒度和显存/通信压力，在 CP=2 已经引入额外 attention context 并行通信的情况下，更大的 chunk 没有明显降低调度开销，反而放大了 prefill 阶段排队、跨 rank 同步和流水线等待成本。C60 下 Mean TTFT 平均达到 25159.77 ms，说明高并发长上下文请求下首 token 等待明显偏高。

## 建议

不建议采用 `TP=8, CP=2, PP=4, DP=1, chunked-prefill-size=8192` 作为当前环境的推荐配置。

当前更优选择仍是 `TP=8, PP=4, DP=1, CP=1, chunked-prefill-size=4096`。如果继续探索 CP 参数，建议优先保留 `chunked-prefill-size=4096`，再单独验证 CP=4/8 的可启动性和吞吐表现，避免同时放大 CP 并行和 prefill chunk 粒度带来的叠加影响。
