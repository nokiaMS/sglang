# DeepSeek-V4-Pro TP8PP4 HiCache 性能测试分析

## 测试配置

- 模型: DeepSeek-V4-Pro
- 硬件: 4节点 × 8×H800 80GB (32 GPU)
- 框架: sglang v0.5.12.post1
- 并行: TP=8, PP=4
- HiCache: enabled (ratio=2.0, write_through, direct IO)
- mem-fraction-static: 0.90
- max-running-requests: 64
- swa-full-tokens-ratio: 0.2
- 代码修复: hybrid_pool_assembler.py start_layer 偏移修复

## 关键发现

### 1. 吞吐量与并发度关系

- **Input throughput**: C10→C30 增长约 95%（5974→11653 tok/s），C30→C60 仅增长约 10%（11653→12869 tok/s），接近饱和
- **Output throughput**: C10→C30 增长约 56%（29.5→46.2 tok/s），C30→C60 增长约 10%（46.2→51.0 tok/s）
- **系统在 C30 附近已接近吞吐量上限**，C60 并发下吞吐量几乎没有提升

### 2. 延迟分析

- **TTFT 急剧增长**: C10 约 2s → C30 约 7s → C60 约 45s。C60 的 TTFT 相比 C10 增长约 22 倍，说明排队等待严重
- **TPOT 在 C30/C60 下接近**: C30 均值 958ms，C60 均值 945ms，但中位数分别为 547ms 和 570ms。高并发下尾延迟（P99 TPOT）在 C30 时反而更高（10.9s vs 8.5s）
- **E2E 延迟**: C60 的 E2E 延迟均值 216s，中位 199s，表明大部分请求需等待超过 3 分钟

### 3. 延迟分布特征

- **TTFT 长尾严重**: C60 的 P99 TTFT 达 125s（中位 39s），表明部分请求在队列中等待极久
- **TPOT 双峰分布**: 中位 TPOT 在 C30/C60 下约 540-570ms，但均值在 940-960ms，P99 在 8.5-11s，说明存在显著的调度抖动
- **ITL 尾延迟**: Max ITL 在 C60 下达 44-45s，C30 下 32s，C10 下 7-9s，高并发下 token 间延迟抖动显著增大

### 4. 系统瓶颈判断

- **Prefill 瓶颈**: 随并发增加，TTFT 增速远超 TPOT，表明长上下文（50K input）的 prefill 阶段是主要瓶颈，导致请求排队
- **KV Cache 容量**: HiCache ratio=2.0 扩展了 KV cache 容量，但 max-running-requests=64 限制了并发调度，从实际并发度（C60 约 55.4）来看已接近上限
- **PP 通信开销**: 4 级 PP 的跨节点通信在 prefill 阶段引入固定延迟，低并发时不显著，高并发时排队效应放大

### 5. 稳定性

- C10 三次测试结果标准差小，吞吐量波动 <4%
- C30 三次测试一致性极好，波动 <2%
- C60 三次测试一致性同样良好，波动 <2%
- 系统在各并发度下表现稳定

## 建议

1. **最优并发度**: C30 是吞吐量与延迟的较好平衡点，Input throughput 达 11.6K tok/s，TTFT 约 7s 可接受
2. **降低 TTFT**: 可考虑增大 max-running-requests 或优化 prefill 调度策略（如 chunked prefill），以减少高并发下排队时间
3. **TPOT 优化**: 中位 TPOT 约 540-570ms 表明 decode 效率尚可，但 P99 TPOT >8s 说明调度抖动需关注
4. **HiCache 效果**: 需与无 HiCache 的对照组比较来量化 HiCache 对吞吐量的贡献
