# 启用 CUDA Graph 测试结果分析（对比禁用 CUDA Graph）

## 测试配置

| 配置项 | 值 |
|---|---|
| 模型 | DeepSeek-V4-Pro |
| GPU | 4节点 × 8×H800 80GB |
| TP | 8 |
| PP | 4 |
| mem-fraction-static | 0.95 |
| max-running-requests | 64 |
| swa-full-tokens-ratio | 0.2 |
| hicache-ratio | 2.0 |
| disable-overlap-schedule | 是 |
| **disable-cuda-graph** | **否（启用 CUDA Graph）** |

唯一变更：去掉了 `--disable-cuda-graph`，启用 CUDA Graph。

## 测试结果

| 并发 | CUDA Graph | 结果 |
|---|---|---|
| C10 | 启用 | **崩溃** — 服务在处理少量请求后崩溃 |
| C30 | 启用 | **崩溃** — 同样在处理少量请求后崩溃 |
| C60 | 启用 | **跳过** — 服务已不稳定 |
| C10 | 禁用 | 正常 — 6095/6145/6107 tok/s |
| C30 | 禁用 | 正常 — 10316/10815/10683 tok/s |
| C60 | 禁用 | 正常 — 12291/13151/12830 tok/s |

## 崩溃分析

### 崩溃模式

两次崩溃表现完全一致：

1. **服务启动正常** — CUDA Graph 捕获成功（bs=[1,2,4,8,12,16,24,32,40,48,56,64]，每 GPU 约 0.46 GB）
2. **开始处理请求** — Prefill 正常执行，进入 Decode 阶段后 CUDA Graph 被激活（日志中 `cuda graph: True`）
3. **约5-30秒后崩溃** — Scheduler 抛出异常，gloo 连接断开

### 错误信息

```
Scheduler hit an exception: RuntimeError:
[/pytorch/third_party/gloo/gloo/transport/tcp/pair.cc:547]
Connection closed by peer [172.16.xxx.xxx]:xxxx
```

随后收到 `SIGQUIT` 信号，服务完全退出。

### 根因分析

**CUDA Graph 与 DSV4 PP=4 HiCache 模式不兼容。**

具体原因：

1. **CUDA Graph 要求计算图静态** — CUDA Graph 在捕获时固化了所有 GPU 操作和内存地址。Decode 阶段使用 CUDA Graph 时，所有 GPU kernel 和 tensor 地址被固定。

2. **HiCache 异步操作破坏图静态性** — HiCache 的 Host↔Device 数据搬运（`hicache-io-backend direct`）是异步 DMA 操作，需要在运行时动态调度。当 HiCache 需要换入/换出 KV cache 页时，这超出了 CUDA Graph 捕获的静态图范围。

3. **PP=4 多节点通信被中断** — 在 PP=4 模式下，Pipeline Parallel 依赖 gloo/nccl 进行跨节点通信。当 CUDA Graph 执行的 decode 操作与 HiCache 的异步 I/O 产生竞争时，可能导致通信超时或状态不一致，进而触发 gloo "Connection closed by peer"。

4. **崩溃时间与 decode 进入一致** — 日志显示崩溃发生在 Decode batch 使用 CUDA Graph（`cuda graph: True`）之后不久。Prefill 阶段不使用 CUDA Graph（`cuda graph: False`），因此不会崩溃。

### 崩溃时间线（C30 测试）

| 时间 | 事件 |
|---|---|
| 12:37:34 | 服务就绪 |
| 12:38:27 | 开始处理 Prefill 请求 |
| 12:38:33 | 所有请求 Prefill 完成，进入 Decode |
| 12:38:33-34 | Decode batch 使用 `cuda graph: True` |
| 12:38:37 | Scheduler 异常，gloo 连接断开 |
| 12:38:37 | SIGQUIT，服务退出 |

**从 Decode 使用 CUDA Graph 到崩溃仅约3-4秒。**

## 结论

| 结论 | 说明 |
|---|---|
| **DSV4 PP=4 + HiCache 禁止启用 CUDA Graph** | 在此配置下启用 CUDA Graph 会导致服务在处理任何实际请求后短时间内崩溃 |
| **必须使用 `--disable-cuda-graph`** | 这是 DSV4 PP=4 HiCache 模式的硬性要求，不是性能优化选项 |
| **崩溃非 OOM** | 崩溃时 GPU 内存充足（avail mem ~34 GB），问题出在 CUDA Graph 与 HiCache 异步操作的兼容性 |
| **影响范围** | C10/C30/C60 所有并发均崩溃，说明问题与并发数无关，而是 CUDA Graph 本身的兼容性问题 |

## 性能影响评估

启用 CUDA Graph 本意是优化 decode 性能，但在 DSV4 PP=4 HiCache 配置下完全不可用。禁用 CUDA Graph 的代价：

- **Decode 延迟**：无 CUDA Graph 加速，decode 的 kernel launch 开销略高
- **实际影响有限**：DSV4 的 decode 主要瓶颈在 MoE 计算和 HiCache I/O，而非 kernel launch overhead
- **GPU 内存节省**：禁用 CUDA Graph 每卡节省约 0.46 GB（12 个 batch size 的图缓存），这些内存可用于 KV cache

## 建议参数（更新）

在之前建议的参数基础上，**必须保留 `--disable-cuda-graph`**：

```bash
--tp 8 --pp-size 4
--mem-fraction-static 0.90
--max-running-requests 64
--swa-full-tokens-ratio 0.2
--hicache-ratio 2.0
--disable-cuda-graph          # 必须禁用
--disable-overlap-schedule    # PP>1 自动禁用，显式指定
--enable-hierarchical-cache
--hicache-write-policy write_through
--hicache-io-backend direct
```
